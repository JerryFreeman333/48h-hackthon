## 1. 先给出最强反对意见

这个产品最容易失败的方式，不是页面不好看，而是“B 获得的信息很薄，C 却输出很厚的报告”。真实岗位是否在招、固定底薪、实际工作内容、合同主体、带教和团队情况如果没有材料，模型再流畅也不能补齐。最后用户得到的可能只是通用 AI 已能给出的泛泛分析，而不是值得单独付费的决策信息。

因此，不能把“JSON 能连起来”“报告能生成”“用户觉得文字不错”当作产品成立，更不能据此宣称能预测录用、晋升、公司倒闭或职业成功。

可以成立的最小价值是：在明确的信息范围内，发现个人硬约束冲突；把已知事实、推断和未知分开；给出对应材料的解释；生成能核验未知的具体问题；保持来源和版本可追溯。

### 4.2 C 可在本目录解决，但须写入实现说明

1. **快照与复现**：公共 MatchReport 只有证据/事实/覆盖快照，缺画像、公司、岗位标题/薪资等完整输入；它单独不能重现整个页面。按 C 文档存储要求，C 的私有 ReportSnapshot 保存 profile、intentContext、bundle、输入哈希、规则/prompt 版本。公开 MatchReport 不擅自加字段；JSON 复现包采用另有版本的 C 私有封装，说明包含私人材料，只对所有者导出。
2. **问题目标字典**：questions.resolves 是 string[]；约定可追踪目标路径/标准 key，不能任由模型发明无法回写的字段。展示“这个问题解决哪项未知”，不实现新的企业事实同步机制。
3. **动作词的中文说明**：hold＝暂停当前关键操作并核验；deprioritize＝当前已确认约束不合，降低优先级；verify_first＝先解决关键未知；explore＝可进一步了解，不等于该岗位确认在招；insufficient＝没有可用候选/基本可判断材料。
4. **同事实、不同影响**：用户差异只改变解释、约束和动作，不改变 bundle 里的任何公司/岗位 Fact；可用不可变对象和哈希回归检查。
5. **输入真实性分级**：任意导入 JSON 的 verified/live 字符串不是现实真实性证明。demo/manual 导入需标来源；live 只能消费经过鉴权的可信 B 快照。来源真实性由核验流程负责，C 的 schema 校验不冒充重新工商调查。
6. **职责、成长、下一步**：若 1.0.0 不新增结构，可先通过 dimensions/reasons/questions 与规则衍生动作呈现；不得为了页面方便私加公共 nextActions 等字段。确有结构化交换需要时共同升级。
7. **取消与反馈**：文档有 cancelled 和 ReportFeedback，但未完整列 C 的取消/反馈接口；取消优先使用公共任务能力，反馈接口须按本轮验收范围共同确定，不凭空扩成功能体系。

### 4.3 文档局部歧义需明确记录

- C 第 4 节给出优先级：insufficient → hold → deprioritize → verify_first → explore；第 8 节又概括“主体歧义→verify_first”。若主体歧义同时存在已确认硬冲突，应按哪条？提案：以第 4 节明确优先级为准，并在 reasons 同时保留主体未知；需三人确认，不把歧义静默吞掉。
- “基本输入不足”不能包含一切资料缺失，否则财务未知会把任何有价值判断都降为 insufficient。结构非法/未确认画像应 API 拒绝；资料部分缺失走 partial；无候选才产生空结果及 insufficient 说明。
- 五维中“personal_fit: supported”不是“此人适合”。样例恰好是证据支持了不接受销售 KPI 的冲突。

本轮没有改变 schemaVersion=1.0.0。新增公共字段、枚举、key 的语义须同步公共定义、三方样例和测试；版本号升级由共同维护人决定。

## 5. C 的判断流水线

### 5.1 推荐架构

```text
可信 UserProfile + SearchIntent 上下文 + CandidateBundle
    ↓
运行时 schema /版本/权限/模式/修订关联验证
    ↓
主体、引用图、key语义、数字单位、日期与字段来源验证
    ↓
可溯源的职责整理（缺事实则只解释或保持未知）
    ↓
确定性硬约束 → 确定性动作 → 多原因保留
    ↓
模板五维报告（不依赖模型）
    ↓
可选 AI：职责语言、目标权衡、具体问题；不产生新的公司事实
    ↓
结构/引用/语义/数字/不确定性/规则一致性检查
    ↓
不可变 ReportSnapshot
    ├─ 页面
    ├─ 同维度比较
    ├─ Markdown
    └─ 所有者 JSON 复现包
```

AI 可以提出语义解释，但不能把自己的职责分类直接升级为 B Fact，再触发硬冲突或 hold。缺少可用结构化事实时，将缺口反馈 B 或保留 unknown，不在 C 悄悄新增外部检索。

Zod 官方文档提供运行时 parse/safeParse 和类型推导能力。[S1] 它验证结构和显式检查条件，不会自动判断某片段是否支持一个语义结论。因此不能把“Zod 通过”写成“事实正确”。

### 5.2 硬约束的可执行规则

仅对本人 confirmed 的 hard 约束生效。未知偏好不默认接受。初版只使用公共已列出的 city、min_fixed_monthly_salary、accept_sales_kpi、accept_travel、accept_outsourcing；事实 key 的具体值类型先共同注册。

**销售 KPI**：

- 用户已确认不接受 + 有支持的岗位销售 KPI 材料 → fail。
- 用户已确认不接受 + 材料明确无此要求 → pass。
- 材料缺失、真假不明、主体错位或来源冲突 → unknown；不能“没写销售”就当不存在。
- 用户明确接受不等于销售能力已被证明；不再用这一限制否定岗位，但能力/目标仍另行解释。

**最低固定税前月薪**：

- 比较之前必须确认用户阈值的单位和岗位的币种、税前后、fixed、月薪口径一致。
- total/税后/不明支付月份的年薪，不自行换成固定税前月薪；没有可靠转换资料时 unknown。
- 设阈值 T，已核验固定区间为 [L,U]：L≥T 才能说披露区间全部达到该收入下限；U<T 才是明确低于；L<T≤U 则实际 offer 未定，unknown，询问固定待遇。
- “区间部分可能达标”不能叫 pass。JD 披露达到阈值也不代表已经拿到该薪资 offer。
- 缺单位、缺事实溯源、数值关系非法不得靠模型补齐。

**城市**：只对用户确认的硬城市范围判断；SearchIntent.cities 的一般意向不能自动变成新硬约束。使用共同确定的地理规范化，不用字符串包含法把“全国/上海优先”判为确定在上海。

**出差/外包**：看对应岗位事实；公司注册地址不同、品牌与合同法人不同，不能单独证明外包；合同性质不明就 unknown。

### 5.3 有限动作规则

按确认后的优先级执行，不累计成一个综合分：

1. insufficient：没有可用候选/基本可判断内容。
2. hold：有限规则登记中直接材料支持当前关键核验风险；如入职前向私人账户付款的材料，动作是暂停该付款并核验，不是给公司定“诈骗”。
3. deprioritize：已确认 hard fail；软偏好不能抵消。
4. verify_first：主体/关键条件未知或冲突，且没有更高优先动作。
5. explore：有正向适配依据、没有上述阻断；仍不保证录用、安全或当前招聘。

“关键未知”的目录应共同确定，并与用户约束/报告范围相关；不是任意一项公司资料缺失都永久阻止 explore。匿名讨论、参保少、小公司、共址或地址变化不能单独触发 hold。

### 5.4 语义校验与安全

分层验证：

1. 结构：五维且各出现一次、合法枚举、无空报告、无截断。
2. 引用：Fact 和 Evidence 存在、ID 不重复、公司/岗位/scope 一致。
3. 命题：证据到底支持了什么；“收集反馈”不能推出“参与产品设计”，标题“产品运营”不能推出“没有销售”。
4. 时间：历史已移出不写当前异常，采集时间不充当事件时间，未知日期保持未知。
5. 数值：薪资口径、币种、职责比例、概率不被编造。
6. 人：兴趣不代替能力，用户目标/经历出自确认画像。
7. 输出：模型不能改变规则动作、硬约束结果和 B 原始事实。

前两层可较强自动化；命题支持和开放式推理不能在当前方案中保证完全自动正确。第二模型最多作为辅助审查，不能用“两个模型同意”冒充已验证真相。规则限定、证据片段对齐、人工真材料评审与保守降级仍必需。

JD、简历、帖子中都可能含不可信指令。OWASP 官方项目记录了来自外部内容的间接提示注入和权限隔离思路。[S4] C 的提案是：固定 provider 调用由服务器代码执行；分析模型无任意浏览器/抓取工具、无项目间访问能力，模型文本不能修改动作、费用或调用次数。密钥不进入提示词。即便 system prompt 被误读，确定性规则和后验检查也要阻断影响。

网页关闭原始 HTML 渲染、检查链接协议、转义导出内容；不可把导入 JSON 或材料字符串直接当 HTML/可执行 Markdown。

## 7. 持久任务、快照、幂等与成本

### 7.1 报告与运行状态分离

任务状态按文档：queued/running/completed/partial/failed/cancelled。Report.completeness 表示资料/规定阶段覆盖，不由“调用成功”决定；任务跑完仍可能是 partial 报告。

C 私有快照至少保存原始已确认输入、输入哈希、规则/prompt/运行时 schema 版本、生成时间和模型执行记录。用户更新任何关键材料，创建新 run 和新 report version；B 刷新不能偷偷改旧报告。网页和导出读取同一快照，不再让模型重写。

### 7.2 幂等与权限

- 幂等作用域：所有者/项目/C 操作/幂等键；按 canonical JSON 计算输入哈希。
- 相同键且相同输入返回同一任务；同键不同输入返回版本/幂等冲突，不覆盖旧 run。
- 并发靠数据库唯一约束/事务，不能只查内存。
- POST、GET run、GET report、Markdown/JSON export、update 均验证项目所有权。
- 无生产鉴权时只能显式本地演示；live 启动/请求不能悄悄退化成无鉴权服务。

### 7.3 执行器

用公共持久执行器，C 注册领域任务；阶段产物落盘、租约/心跳/取消标记由公共能力提供。Next.js 官方 after 文档说明其执行时长受平台或路由 maxDuration 约束。[S2] 这不足以满足本产品的恢复、幂等和取消要求，因此不能把响应后的内存 Promise/after 本身视为持久队列。

worker 重启时可从已完成阶段恢复，但“任务幂等”不等于“外部收费只发生一次”。若调用已发出、响应丢失，其执行/费用状态可能 unknown；不支持供应商幂等时不能盲目重发以假装安全恢复。记录 pending/unknown outcome，按供应商能力或人工核验处理。

### 7.4 预算与延迟

文档默认每 run 最多 8 次模型调用（包括修复），单请求 30 秒，整体 120 秒软上限。这是配置，不是实测 SLA。8×30=240 秒，所以实现必须同时检查剩余调用数、时间和金额；不是把每一次都串行等满 30 秒。

提案：

- 用固定阶段计划，不做自由 agent 循环；同一 bundle 合并上下文，先评估是否需要模型。
- 每次调用前检查/预留最大输入、输出、价表与必要换算所对应预算；剩余预算不足不调用。
- 一次修复仍失败，保留规则产物并 partial；修复/重试都计入次数和费用。
- 使用量/价格/转换依据缺失时记 unknown，不能记零；无法给出有意义费用上界时关闭自动付费调用。
- 取消停止后续调用，不承诺已发出的请求不收费；失败费用仍保留。
- C 模型费用和 B 数据费用分项，套餐费用在公共成本层另行摊销，不重复计每次边际费用。

### 7.5 商业成本与验证

不建议目前给一个看似精确的售价或利润。没有供应商合同、实际 tokens、人工分钟数和获客数据，利润无法算出。

每份交付的试验成本同时记录：B 数据边际费用、C 模型全部调用（含失败/修复）、人工处理时间、存储/任务成本。供应商固定套餐、获客/服务/退款成本分开记录。看成本分布，不只看平均；平均交付成本的分子要包含最终失败、取消和重做的付费调用，分母才是已交付报告数。

收费模式与真实订单/退款由公共产品任务定义，C 不新增支付，也不相信客户端 paid=true。

## 8. 开发流程与三人协作关卡

### 8.1 Phase 0：建立共同实施基线

**产物**：共同仓库地址、公共维护人、所有权表、4 对象运行时 schema、规范 key/单位/事实时序字典、固定 fixture、runtime port 约定、锁文件与 CI、契约决策记录。

**C 可以立即做**：把现有公共样例当只读输入，列规则真值表、错误清单、测试夹具和模板草图；本轮已经产出审查记录。

**通过条件**：三模块同一版本；最关键 key 可执行；意向能正确绑定画像；公共能力有人负责。不将 C 变成无偿承包全部底座的成员。

### 8.2 Phase 1：C 离线核心与模板报告

**产物**：schema 接入、引用/主体校验、五种硬约束处理框架、动作优先级、五维模板、关键未知与问题字典、输入/结果不可变约束、扩展测试 fixture。

**独立方式**：直接用 JSON，模型关闭，网络关闭；不依赖 A/B 在线。公共 schema 未落地时只基于只读契约做测试适配，不发布另一套正式公共 schema。

**通过条件**：公共样例得到 deprioritize；total 不被当 fixed；空候选不造职位；同公司不同用户不改事实；非法引用可定位失败；所有五维存在。

### 8.3 Phase 2：API、快照与基本任务

按原文实现：

- POST `/api/c/matches`
- GET `/api/c/runs/:id`
- GET `/api/c/reports/:id`
- GET `/api/c/reports/:id/export?format=md`
- POST `/api/c/reports/:id/update`

JSON 导入/导出为 C 独立验收入口，需要明示 artifact 结构，不改 MatchReport 交换结构。

**产物**：领域 run handler、快照 repository、输入哈希、版本、幂等、所有权钩子、阶段结果、已知缺口状态。使用公共 runtime；测试适配器只用于显式 local demo/test，不能混入 live。

**通过条件**：相同请求不重复建任务；旧报告不被更新覆盖；A/B 不运行时样例可从 API 生成/导出；跨用户读取和导出被拒绝。

### 8.4 Phase 3：独立入口和报告页面

**入口**：`/demo/c`；正式 `/reports`，宿主/路由挂载由公共维护人负责。

**产物**：JSON 导入、首屏动作/最多 3 理由/首要问题/coverage，五维、约束、职责解释、证据抽屉、同维度比较、移动单列、键盘操作、Markdown/JSON 所有者导出。

**通过条件**：网页、比较和导出数据一致；unknown 不为零/绿灯；没有总匹配率/冠军；无 URL 显示提供方式；每条问题能追踪待核验项；导入失败给具体路径和原因。

### 8.5 Phase 4：可选 AI 与语义评审

复用公共模型客户端。C 只提交本模块 prompt、响应 schema、预算需求和领域校验；没有密钥时保持规则/模板输出并标缺少语言解释阶段。

**产物**：固定 prompt 版本、可控阶段计划、结构/数字/引用/规则不变量校验、最多一次修复、partial 降级、真实材料人工评审集。

**通过条件**：语义不支持能拒绝/降级；模型不会覆盖动作或捏造公司事实；含注入的 JD 不获得额外权限；预算与缺失费用记录真实。

### 8.6 Phase 5：故障、联调与真实人工闭环

**产物**：worker 重启/取消/超时/引用故障测试，C 与 runtime 契约测试，A→B→C 集成测试，真实材料评审记录和成本记录。

**通过条件**：画像更新、旧意向、主体同名、无候选、B 部分失败、C 模型失败、未知薪资、跨用户访问、导出一致性等路径全部有实际记录；未接的数据源仍显示未接。独立完成与整体联调分别签收。

排期先按关卡而非“某天必上线”：本轮没有开发者可用工时、共同底座负责人、部署目标和供应商响应时间，无法可靠估日历日期。完成 Phase 1 后再用实际吞吐估剩余工作；外部等待与 C 净开发时间分开。

## 11. 真实用户与商业验证流程（产品团队任务，不扩 C 范围）

建议的小型探索试验：10–15 名正在实际求职的用户，每人 1–3 份真实 JD；这是资源可控的提案数量，不是市场效果的统计依据。资料由 B 走人工真实流程，C 分析，人工审查关键结论。

与相同材料下的“只看 JD”或通用 AI 分析比较：

- 是否发现具体、可核查、非显而易见的冲突或问题。
- 每条事实性结论是否真的由来源支持；严重错误单独计数，不能被文字满意度抵消。
- 用户是否实际向 HR/面试官提出核验问题并获得新信息。
- 有多少只是兴趣解释，多少帮助真实缩小候选/避免不符硬约束。
- 实际处理时长、修订次数、总调用成本、人工成本。
- 在明确报价和报告范围后是否发生真实支付；“我愿意考虑”不是支付。

上线门槛建议：合成确定性规则、权限与不变量验收中跨主体引用、越权、静默 demo 混入、未知当零等错误为零；这只是该验收集中的要求，不是生产零风险承诺。真实材料发现严重事实错误时修复后重跑评审；缺来源的公开事实性断言不得放行。

若首轮验证发现大多数报告仅重复 JD/公开信息、关键未知问不出答案、对比普通 AI 没有增量，不应只换更大模型或再堆页面，应收缩报告承诺和覆盖范围后重新验证。
