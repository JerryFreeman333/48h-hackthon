# 产品演示与验收入口

当前是本机可运行产品原型。使用 http://127.0.0.1:3000/，浏览器会话保存需求与报告；同一浏览器继续可恢复本机归档。不要把合成演示公司当成现实调查结果。

## 先验证最短路径

1. 首页选择“分析这份工作”，输入实际考虑的岗位名称和原始JD，公司、城市、链接可以暂空。
2. 可以选择已确认本人需求，也可明确勾选暂时全部未知。后者不能产出“适合你”的声称。提交后自动沿用新创建的确认版本。
3. 先看首屏动作和必要条件，随后看用户关注清单；各项未知、冲突及来源应能解释。不能出现自创综合分或冠军。
4. 连续输入第二份JD，再到“比较候选岗位”先选同一需求版本，再选择两份报告。页面显示每岗位最近生成的报告；旧回复/修订不会变成多个候选，旧版本仍可在历史打开。应使用同一需求记录、确认版本和资料模式；不是把同一岗位的不同报告当成两个候选。

## 再验证需求与核验反馈

1. 首页“整理我的求职需求”从一份新记录开始。七主题可选重点/次要/未知，重点可要求先核实或允许带着未知继续；现实条件另行确认。
2. 用这份需求分析JD。即使另一硬条件通过，尚未明确的硬条件仍使个人适配保持未知；销售拒绝与明确销售KPI事实冲突时应显示暂缓，软偏好不得抵消。
3. 报告里选择“补充核验回复”，针对对应岗位问题保存招聘方回复和可选来源。新报告保留这段内容，但固定标记用户提供、待核验；它不会自动解除未知。
4. “修改需求后重新分析”必须打开原报告对应的需求，确认更高版本。变化区显示条件、未知意愿与最终下一步前后值；岗位和证据仍是原快照，不刷新调查日期。规则升级也会说明差异不能全归因于需求。
5. 旧报告与旧MD/JSON必须继续读取原始版本；新报告可以回到补充前/修改前报告。

## 更新岗位材料

报告“更新这份岗位JD”用同一需求版本替换本次岗位材料并另存报告；公司/实际岗位变了应另建候选。提交同岗位确认后，变化区显示正文/来源变化和最终动作前后。旧回复作为历史未核验记录保留；新JD不会替旧回复背书。旧薪资/在招声明不自动沿用，页面录入时间不证明招聘仍有效。更新前报告保留。

## 你醒来后优先做什么

先用2–3份你们目标用户真实会拿来的JD跑一次，检查他能否说清楚：哪些是事实、哪些还未知、下一步要问什么。根据这些反馈收敛报告长度、提问顺序和前端一致性。队友继续提供资料，你这边优先完成材料审核/接入及产品流程，而不是增加测评或支付。

爬虫资料进入B后还需要准确绑定招聘/签约主体、岗位或团队范围、来源日期和核验状态，再进入报告。七主题事实协议见 NEEDS_EVIDENCE_PROTOCOL.md。账号与生产数据库、授权真实数据源、资料核验器和线上部署都未在本机原型里完成。
