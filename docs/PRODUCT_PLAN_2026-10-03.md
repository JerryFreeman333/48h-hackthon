# 求职 X-Ray：下一阶段产品方案

## 产品方向

第一版帮助求职者判断具体工作是否值得继续，并告诉他下一步该核实什么。最重要的交付是可信的岗位判断与行动清单。用户是否找到工作方向是另一条入口；不强制先做人格测评、上传简历或填写完整问卷。

已有代码的价值：A 可以保存用户声明需求及确认版本，B 可以保存岗位资料和证据，C 可以根据约束输出可追溯报告。ABC 已有基础骨架。开工时主要缺口是七主题需求未被后续流程回应，修改条件或补充资料之后的回路不完整。本次已补齐本机产品闭环，真实资料生产与独立核验仍需接入。

## 两个入口，同一个终点

1. 已有岗位：粘贴 JD → 确认最少需求或暂时未知 → 岗位报告 → 核验问题 → 补充资料 → 新版报告。
2. 还没选岗位：整理七主题需求 → 选择方向与候选 → 同一份岗位报告。

已有岗位不能因不符合搜索条件而消失。报告要区分：信息是否存在、证据是否可靠、用户条件是否满足。用户暂不填写需求时，允许调查岗位，但个人适配保持未知。

## 你这边负责什么

队友继续采集资料。你负责把资料变成可以用于决策的产品：先明确目标用户与使用场景，再确保需求、证据和结论是一一对应的，最后验证普通用户能否看懂并采取下一步行动。

建议先选“已经拿到 JD、正在决定是否投递或继续面试的毕业生”作为测试对象。无需先做大规模市场定位；用三至五份真实 JD 做完整走查，观察用户能否回答：我在乎什么？这里有哪些冲突？还缺什么？下一步问谁、问什么？报告有没有因此改变我的决定？

你的近期投入应放在：定义需求与事实对应关系；设计报告首屏；验证修改与补充之后结论为何改变；确认爬虫交接字段与证据范围。不要先花时间完善收费、社区或扩大问卷。

## ABC 职责

| 模块 | 应负责 | 必须交接 |
|---|---|---|
| A | 用户需求、未知处理意愿、确认版本 | 七主题重点和明细、五类现实条件、需求版本 |
| B | 岗位、主体、事实及证据调查 | 原文/链接/日期、岗位或团队范围、核验状态、缺口 |
| C | 判断条件冲突、回应需求、解释与行动 | 已知/未知/冲突、引用依据、待核验问题、版本差异 |

七主题不是匹配分。用户关注“带教”时，应回应有哪些可核实材料和什么仍未知；不能从 JD 的“成长空间大”推断已经满足需求。用户选择“先核实再决定”时，该重点未知应成为行动门槛。

## 报告应该先展示什么

首屏按顺序呈现：建议下一步动作、最关键条件冲突、用户关注项目的回应、需要问招聘方的问题。每条结论有证据或明确缺口；技术编号与完整证据放在可展开详情。比较候选时，用同一需求版本逐项比较，未知不计零、不自动排冠军。

修改个人需求产生新版本；补充资料产生新证据快照；旧报告保持不变。只有真正被补充材料解决的问题才变成已回应，用户点“已核实”不能自行把招聘方声明升级成事实。

## 八小时实施顺序

时间是推进顺序参考，以测试和实际可交付为准，不承诺堆满全部功能。

| 阶段 | 交付目标 | 验收 |
|---|---|---|
| 第一段 | 直接 JD 分析入口 | 人工 JD 不混演示；城市冲突仍保留；可在浏览器得到报告 |
| 第二段 | 七主题调查计划与报告回应 | 选项会改变调查问题；重点未知和处理意愿真正影响下一步 |
| 第三段 | 条件修改、报告恢复与版本记录 | 重启可恢复；旧版不变；新结论可解释 |
| 第四段 | 候选比较、核验反馈及界面整理 | 同版本逐项比较；补充证据有可追溯变化 |
| 最后一段 | 回归、构建、浏览器验证与交接 | 真实完成项、剩余问题和启动方式都可复查 |
