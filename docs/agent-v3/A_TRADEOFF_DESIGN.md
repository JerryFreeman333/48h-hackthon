# A 求职取舍重塑：设计依据与实际复用

日期：2026-10-13。A 指用户需求档案，B 指找职位，C 指核查所选职位与企业。本文取代“多加细分理想条件就能获得真实需求”的设计判断；不替代历史版本的归档说明。

## 本轮要解决的问题

原流程按七个主题分别询问理想条件，用户容易把全部优点都选上。新流程以混合的工作情境询问实际取舍，条件变化时再问接受范围；最后才归纳到既有主题和 B/C 可读取的具体要求。界面只呈现连续答题，不显示主题树、计分模型或人格类型。

题目不会隐瞒产品目的：开头说明这是帮助理解求职选择的问答。单题不标注内部维度，是为了减少按栏目全选，并非声称能绕过用户意识判断其“真实人格”。

## 题目和判断的约束

1. 本产品题目与选项为原创求职情境，不是已验证中文心理量表。功能测试通过不能证明信度、效度或能预测求职满意度。
2. 比较选项均包含可理解的收益和代价，不设置明显“正确答案”。固定收入与奖金分开，不能把含奖金年薪换算为固定月薪。
3. 以工作安排、协作、任务、合同和兑现为通用描述，不假定用户属于软件、办公室或单一行业。必要信息可以不知道。
4. 相对选择只说明给定情境下更倾向哪项，不推断人格，不伪造稳定的偏好概率，不生成精确心理分数。
5. “看情况”和“不确定”有独立出口。看情况可以进入有界澄清；不确定保留为未知，不无限循环。
6. 后题用于解释接受条件；前题变化时清除失效的后题，并记录原因，不能让旧答案悄悄继续作用。
7. 薪资底线、城市、合同与保障等具体约束只能依据用户直接回答及确认。相对排序不会自动变成硬约束；既有 B 五项检索条件保留字段含义。
8. 保障题区分按规定办理与用户希望优先核查的证据。不设计“愿意放弃法定保障换收入”的选择，也不从用户回答认定企业合法或违法。
9. 排序保留并列、未比较、依赖情境与冲突；没有充分比较时不强造完整 1–7 序列。用户最后可确认或纠正结果。
10. B/C 接收的是可解释、带回答来源的当前需求及未知。取得企业材料、回答问题、证实陈述、满足用户需求仍分别处理；没有核查条件满足时保留未知。

## 验收边界

规则验收检查混合题、条件跳转、未知出口、失效答案清理、排序来源、确认和兼容映射。浏览器验收从 `/profile` 操作真实 HTTP 服务，检查保存恢复、版本重开、修改、手机宽度、关闭回退与 A→B；不使用内部状态注入替代答题。

这是首版可解释的取舍问答。后续认知访谈、跨行业理解度、重复施测稳定性和实际求职效果验证尚未完成；在这些证据出现前不使用“科学测出真实内心”“人格测试准确率”等宣传。

## 本轮代码中的实际机制

- `modules/a-profile/src/needs/tradeoff-catalog.mjs`：原创 14 道混合情境，各主题出现四次；左/右方案轮换利弊，另有最多 8 道有条件的澄清题。每道主情境都有两种选择、两种都可以、看条件、暂不确定。
- `modules/a-profile/src/needs/tradeoff.mjs`：自有枚举校验、后题激活、失效答案审计、提议归纳和本人确认；没有模型调用。取舍关系以题目 ID 为依据，用强连通分量保留循环，输出部分顺序和未比较关系，不计算人格分或偏好概率。
- 确认依据绑定活动答案和问卷版本；改变前题后旧的确认失效。相对选择不直接写成底线，确认后的具体需求仍保留题目来源。
- 后续明确拒绝交换时撤回原情境的排序关系，保留撤回理由，并把拒绝条件作为待确认的具体需求；“继续了解但保留未知”不转成条件满足或可接受结论。
- 含后题条件的比较不进入无条件排序：单独保留条件关系与来源。原情境给出固定税前收入高约 20%，用户却要求至少高 30% 时，原情境不达到所声明门槛；不能仍据此归纳“收入优先于企业持续性”。未知条件也不参与先后计算。
- 会话保存和历史版本使用既有 A 的存储路径；本轮未新增 SurveyJS、XState 或 JSON Forms 依赖。浏览器脚本复用本仓库既有隔离 Next 主机测试方法，属于验证工具，不是外部量表实现。
