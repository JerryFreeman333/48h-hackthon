条件排序修正后，主线程通过实际 HTTP 新脚本验证：合成用户选择形成 A 档案，经 B 选择原始只读企业库记录 16“大华股份／嵌入式软件工程师”，进入 C 并生成 `report-0915c901-794f-48d5-a119-175a09727586`。附表保留 5 条确认需求、10 个未知问题；企业材料不能直接替代取舍条件满足判断。

最终公开 HTTP 验证还确认：q01 的 fixed30 条件与原约 20% 不兼容，不进入无条件先后，C 中有对应警告；重复确认返回 409；改变前题令 review 失效，重新确认生成版本 2；旧 A 版本与原 C 归档重开后保持不变。

证据在 `.data/a-tradeoff-acceptance/` 的 summary、HTML、view 和 handoff 文件。节点重启的本人 cookie 仅保存在忽略的私有 checkpoint，不在文档或提交中公开。用户选择为合成验收需求，企业记录来自真实原始只读库，两者分开标记。网络调查、模型、新爬虫调用均为 0；这不等于本轮取得了新增企业正文。

## 本轮审查后修复的判断问题

- 补上明确拒绝交换的具体需求，并撤回被后题否定的原排序关系。
- “继续了解但保留未知”不再归入条件明确，不添加无依据需求。
- 按条件实际含义跨主题映射，如岗位范围、福利兑现、及时支持与尊重边界；不按题目所属栏目硬套。
- 薪资比较使用固定税前口径，修正两边 10% 的不清楚基准；阶段合同续约不误标为试用期。
- 含后题条件的比较独立存为条件关系；用户门槛超过原情境时明确标记不兼容，条件仍未知时不参与全局先后。原题没有足够信息证明条件成立时兼容状态保留 null。
- 保存期间禁用当前动作，失败后恢复操作；默认入口不因历史旧记录隐藏新流程。

## 保留的限制

取舍问答是产品原创，不能宣称正式人格测评。对没有直接确认的精确薪资、硬约束和排序保留未知。企业条件是否满足仍由 C 核查，不能把 A 选择升级为企业事实。

本轮用户答案为合成验收选择；未以 fixture 冒充真实用户研究或公司来源成功。浏览器只验证 A 与 B 的导航，未点击开始在线调查；本轮没有新增企业网页采集或模型调用。跨行业语言理解、用户是否真正愿意承担所选代价、重复答题稳定性与求职效果尚需真实用户研究。

早期在受限测试环境中的旧测试遇到 TEMP 原子重命名权限错误和 HTTP 等待；使用正常本机权限与工作区 TMP 后正式检查通过。该环境失败不归因于新增取舍功能，也不隐瞒最初失败。

回退方法：设 `A_NEEDS_TRADEOFF_ENABLED=false` 并重启服务。新建记录回到保留流程，既有取舍记录继续按原版本读取；不重算、不改写历史需求或旧报告。

当前本机预览由主线程启动于 `http://127.0.0.1:3261/profile?new=1`。该预览只在本机运行，不是生产部署；分支和提交见本轮 `PROGRESS.md`。
