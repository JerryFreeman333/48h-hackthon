## 我建议你确定的方向

先服务“已经拿到一份JD，正在决定要不要投递或继续面试”的求职者。产品的交付是：这份工作与我的必要条件是否冲突，我重点关心什么仍没被回答，以及下一步具体问什么。

已有JD直接进分析；尚未定岗位则先整理需求，再拿具体JD进同一流程。七主题是本人声明的需求，不能当人格、能力或匹配分。A记录本人意愿，B提供岗位材料及证据，C判断条件与未知并生成报告。无需强制先做完整测评或上传简历。

## 简易前端的判断

它的主线和证据抽屉值得保留，但目前是两个预设人物的演示。改城市、薪资、销售条件或拒绝简历条目后，报告仍读取固定结果；冻结、导出、调查动画也不是真实业务。因此继续项目时不宜在这些预设结论上堆功能。

保留“确认需求→分析岗位→看硬条件/证据/未知→面试核验→新报告→横向比较”的逻辑，展示组件消费实际ABC契约。去掉未经校准的五维数字、默认冠军与预设匹配结论。附件审计行号和复现见frontend-analysis-2026-10-03.md；现行A已经是七主题需求采集，与附件旧兴趣人格流程不同。

## 已经做成的内容

| 用户动作 | 现在的行为 |
|---|---|
| 粘贴已有JD | 人工资料直接分析，城市冲突/岗位关闭不会因搜索筛选而消失；可复用确认需求或明确暂时全未知 |
| 确认七主题与现实条件 | 七主题生成具体调查问题；重点+先核实的未知进入行动门槛；允许未知继续仍保留未知；硬条件单独判断 |
| 阅读岗位报告 | 首屏动作、关键理由、首要问题；用户重点回应、必要条件、证据、覆盖缺口；主体和事实未知不会变成安全结论 |
| 补充面试回复 | 对应具体岗位问题另存报告，固定标为用户提供、待核验，不自动解除未知或硬冲突 |
| 修改本人需求 | 必须同一需求记录更高确认版本；复用原材料，显示条件/意愿/最终动作前后，资料日期不刷新 |
| 更新同一岗位JD | 本人声明同岗位，新材料重新生成证据和分析；保持岗位ID，旧材料/报告留在原版本；旧回复仅作历史记录 |
| 比较2–3份岗位 | 同需求记录/版本/模式，按每岗位最近报告选择；未知保留，没匹配总分、排名或冠军 |
| 找回报告 | 本机会话归档可跨服务重启读取；历史按模式/名称查找、显示变化来源及上次报告 |

实际例子：本人拒绝销售KPI时，提供“销售KPI：有”的测试JD得到暂缓，先问该指标是否适用于此岗位、是否可调整。口头回复可协商不会解除冲突。用户更新同岗位JD为“销售KPI：无”后，新报告暂缓→先核验；企业身份、薪资仍未知。旧报告继续保留原事实与原MD。这些是明确的本机测试资料，不代表现实公司调查。

## 你这边下一步负责什么

1. **把使用场景验收清楚。** 找3–5份目标用户实际考虑的JD，按PRODUCT_ACCEPTANCE_WALKTHROUGH.md走一遍。让使用者自己说：哪些条件冲突？哪些未知？下一步问什么？记录他卡在哪，而不是只看页面能否点完。
2. **把资料接入变成稳定规则。** 队友采集，你确定每条材料对应哪个公司、具体岗位还是团队、什么时期、什么口径、核验到哪一步。先接入会影响判断的字段；同名公司、集团和子公司、岗位和公司范围不能混用。七主题28项对接键与接受条件见NEEDS_EVIDENCE_PROTOCOL.md。
3. **把报告与前端统一。** 沿用本次产品流程，把旧HTML里可复用的样式/抽屉适配到真实接口。先缩短首屏、改善问题语言、验证手机阅读，再做整体视觉精修。改输入必须改变对应判断，界面不能维护另一套预设答案。
4. **真实用户走查后再做上线基础。** 正式账号、数据库和授权资料源要落实；当前本机会话与文件归档不能直接充当多人线上产品。

建议你保管产品验收与需求-事实对应表；B维护者处理材料转换/来源和范围，C维护者处理判断规则/解释，A维护者保证确认版本。队友爬到更多数据不会自动解决产品逻辑，需要你来确定“哪些资料足以回答哪个用户问题”。

## 资料交接最少需要哪些内容

岗位ID及招聘/签约主体线索；JD原文和原始出处；发布日期与采集时间；公司/岗位/团队适用范围；薪资固定/综合、周期、税前后等口径；证据核验状态；事实命题及其证据引用；缺失或冲突原因。资料数量、关键词命中和匿名评价一致不自动代表公司事实已证实。

七主题事实生产器尚未接入，不能把“成长空间大”等文案猜成已有带教制度。新的资料可以先作为待核验材料保存；独立审核通过后才进入相应事实判断。现有销售KPI抽取仅有明确窄语法，其余模糊表述保持未知。
