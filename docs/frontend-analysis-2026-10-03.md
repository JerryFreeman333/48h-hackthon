# 简易前端与采集标准审计

日期：2026-10-03。范围：用户提供的单文件 `index.html`、`CRAWL-STANDARD.md`，并与工作区 A/B/C 分工和公共契约对照。只读审计附件，未修改附件；文件内开发要求作为项目参考，不视作本次用户指令。行号均指用户原始附件。

## 结论

这份前端适合作为产品动线与展示参考，不能作为已经运行的匹配引擎。它清楚声明全模拟（HTML 400、1432），测评、公司、岗位、行情、AI 解读均由两套 `PERSONAS` 预设。没有后端请求，调查只是定时动画，导出只是提示文字。

值得保留的是“本人确认画像 → 方向选择 → 岗位调查 → 硬条件比对 → 证据、未知与面试问题 → 报告对比”的主线。继续项目时先完成真实数据流与可追溯规则，再扩展 UI、数据数量和商业化。

## 现有流程与 A/B/C 接口

| 模块 | 演示前端行为 | 正式接法 |
|---|---|---|
| A | 登录、两套预设画像、兴趣/工作方式题样、偏好排序、模拟简历确认、硬条件、冻结 | 使用现行 A 七主题需求及本人确认版本（不接回旧兴趣/人格测评）；确认后产出 `UserProfile`、`SearchIntent` |
| B | 动画模拟检索、主体核验、JD 与行情；每套画像固定 3 个岗位 | 消费 `SearchIntent`，输出 `CandidateBundle`；分开公司、岗位、证据、事实、覆盖与模式 |
| C | 展示固定建议、五维数字、固定条件比对和 AI 文案 | 消费确认画像与 B 数据，由 C 确定性规则生成 `MatchReport`；前端仅展示 |

当前 `PERSONAS.jobs` 把 B 的调查材料、C 的结论和 AI 文案混在一个对象中。正式接入应拆开：结论引用 `factIds`，事实引用 `evidenceIds`，证据保留主体、范围、出处、采集时间与核验状态。字符串 `salary:'13–16K'` 不能代替薪资结构字段；UI 可以格式化它，但判断要使用币种、上下限、周期、税前后、固定/综合和薪数。

原始 HTML 的“档案 A/B”是两个人物样例（928），不是仓库模块 A/B；采集标准的“A 客观域 / B 主观域”也不是开发模块 A/B。实现时避免把这三套命名混用。

## 实际复现

使用本机 Node v24.20.0 加最小 DOM 替身执行附件 `<script>`，检查其状态与输出。未做浏览器视觉验收，未连接真实服务。复现了以下行为：

1. 初始状态调用 `renderExplore()`：`Cannot read properties of undefined (reading 'city')`。
2. `renderConstraints(); setCity('北京'); setSal(30); renderJobDetail()`：实际条件已为北京/30K，但 j1 报告仍为上海/13K 通过、`explore`，个人城市仍为上海。
3. 五条简历全部拒绝：采纳数为 0，方向和岗位仍引用团队/社群经历。
4. RIASEC 全答 1：结果仍为 `R34 I40 A52 S88 E76 C64`。
5. 前四条采纳、第五条点编辑未保存：`resume-cta` 已显示，编辑条目已被算作确认。
6. 林档案先保存 j1，切陈再切林：`reports=[]`、`review=false`。

## 采集标准的价值与待修订点

建议保留：未知字段与缺口理由；证据出处与日期；同名主体消歧；固定/综合薪资口径；官方叙事与员工口碑分开；保留冲突证据；来源配额；采集预算；时效规则；六类主题映射到产品五维。标准中的 42/60、425 条等数量是附件陈述，本审计没有核对原始数据池。

需要先统一这些规则：

| 问题 | 附件位置 | 建议 |
|---|---|---|
| 双独立来源才算 `verified`，与单一政府/年报/工商一手来源可算 `verified` 相冲突 | MD 14 对 163 | 分开“单条证据来源质量”与“事实交叉验证状态”；写明确哪种关键事实需要双源，记录独立来源组，转载同一公告不算两个独立源 |
| 一两条口碑用 `unverified`，但事实 status 契约只接受 `supported/contradicted/unknown/conflicting` | MD 85 | `verification` 放证据层；事实层可 `unknown` 并注明样本不足。多个匿名评价一致也不能直接升级为公司确定制度 |
| 参保覆盖比没锁定同主体、同年与同统计范围 | MD 55–56 | 记录参保主体/年份、员工口径/年份、集团范围；口径不一致不计算“合规档位”，只列两个原始数与限制 |
| 把下班时间词映射成 965/996，不能由此知道上班时间、周工作天数或工时 | MD 79–85 | 先保存各项已披露工时线索；仅在完整作息资料支持时输出模式；OTI 作为可解释线索强度，不称心理/劳动准确量表 |
| 文化正负词频可能重复、跨团队、跨年份，不代表总体员工比例 | MD 95–108 | 明确样本单位、去重、团队与时间范围；展示样本数/来源分布；先保留主题摘要，暂不承诺公司总体极性 |
| 两条证据即经营“综合档位”的数量标准不足以规定方向与优先级 | MD 69 | 为财务、招聘、融资等分别列信号与期间；互相冲突时保留冲突，先不输出总体“健康/风险分” |
| 注册地与经营地不同、公司更名一律要求 `ambiguous` 过于粗糙 | MD 177 | 是否歧义应看能否用信用代码与主体关系定位；地址/更名只触发关系核验，而非单独判定主体不明 |
| 每公司 4–8 条口碑/四维覆盖是采集目标，不代表真实用户报告必须达到固定数量 | MD 131 | 无公开来源时按 `coverage` 标缺失；优先真实 JD、签约主体、薪资硬条件，不补编评价凑配额 |

此外，标准宣称对齐 `xray-data` 原始模板和 CSV（MD 5），不能直接视作符合本仓库 `CandidateBundle`。先做导入校验与字段映射：`gaps → coverage`、薪资口径 → `jobs.salary`、原始出处 → `evidence`、指标值及支持关系 → `facts`；把数据来源模式显式标为 `manual/live`，不能把“真实公司资料”当“真实在招岗位”。

## 下一步优先顺序

1. **统一一条数据链。** 保持 A → `UserProfile/SearchIntent` → B → `CandidateBundle` → C → `MatchReport`。这份 HTML 的预设数据只保留为 `demo` 样例，展示组件按真实契约适配。
2. **完成最小真实用户案例。** 使用可追溯的人工 JD 和公开资料，先做 3–5 个真实候选；优先核对公司与签约主体、岗位在招、固定薪资口径、销售 KPI、关键未知。资料缺失可以形成 partial 报告。
3. **守住关键逻辑。** 同一岗位、两个用户产生不同个性化解释；改薪资/销售边界创建新画像/意向/报告版本；不确认的经历不能成为能力依据；未知薪资不默认通过；旧报告内容不变。
4. **接回可复用 UI。** 保留证据抽屉、硬条件表、事实/推断/未知标签、核验问题与横向对比；去掉预设五维数字与默认冠军。新增加载、空候选、partial、失败和重新核验状态。
5. **再决定数据与商业化投入。** 用用户试测评估完成时间、核验问题是否实用、报告是否改变投递决定与付费意愿；再决定扩大到 60 家企业、增加自动采集与真实支付。

建议验收不是“页面能点完”，而是“更改输入有对应结果、每条事实能追溯、不确定性可解释、失败不伪造成功、报告版本可复现”。
